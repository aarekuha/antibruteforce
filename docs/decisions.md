# Архитектурные решения

1. Каждое обращение к сервису является попыткой. Результат последующей авторизации не влияет на счётчики анти-брутфорса
1. Сбрасывать только указанные счётчики логина или IP. Счётчик пароля сохраняется и может продолжать блокировать запрос
1. Bucket IP общий для адреса. Его сброс затрагивает всех пользователей за этим адресом, включая NAT
1. Поддержать несколько экземпляров сервиса с общими ограничениями. Попадание запроса на другой экземпляр не должно предоставлять отдельный лимит
1. Обращаться к bucket через интерфейс операций ограничителя. Детали Redis и создания клиента скрыть в реализации
1. Первую реализацию операций bucket выполнить через один общий Redis в режиме standalone. Все экземпляры приложения используют это общее хранилище
1. Атомарно проверять и изменять каждый bucket отдельно.
1. До списков и bucket проверить структуру запроса, обязательные поля и корректность IPv4. При ошибке вернуть ошибку валидации без изменения bucket. Для ограничения использовать поле ip запроса
1. Проверять blacklist перед whitelist, независимо от размера подсетей. При решении по любому списку завершать обработку без изменения bucket
1. Обрабатывать bucket последовательно: IP → login → password. На каждом этапе атомарно проверять и учитывать попытку, останавливаться при первом отказе или ошибке. Предыдущие списания сохранять
1. Различать ok=true, ok=false, ошибку валидации и техническую ошибку. При технической ошибке не подменять результат штатным отказом или разрешением; не откатывать предыдущие списания
1. Не повторять автоматически списание с неизвестным результатом.
1. Задать лимиты при создании ограничителя: N для логина, M для пароля, K для IP. Использовать одинаковые лимиты и TTL на всех экземплярах.
1. Использовать интерфейс BucketLimiter с TryConsume(ctx, key) (bool, error) и Reset(ctx, keys) error. Для TryConsume передавать один ключ, для Reset — все выбранные ключи
1. Использовать целый запас N/M/K без постепенного пополнения. При успешном списании уменьшать запас на один и устанавливать TTL заново на 60 секунд. При нуле возвращать отказ без изменения счётчика и TTL. После истечения TTL отсутствующий bucket снова означает полный запас. Ручной сброс удаляет bucket
1. Хранить число использованных попыток. Выполнять `INCREX key BYINT 1 UBOUND limit EX 60`. Разрешать попытку при возвращённом приращении 1.
1. В комментарии рядом с вызовом `INCREX` пояснить атомарность списания, полный сброс по TTL и сохранение TTL при отказе.
1. Использовать ключи `abf:v2:ip:<IPv4>`, `abf:v2:login:<SHA-256 логина>`, `abf:v2:password:<HMAC-SHA-256 пароля>`. Формировать ключи внутри Redis-адаптера одинаковым способом для проверки и сброса
1. Принимать исходный пароль в запросе, вычислять его HMAC-SHA-256 с общим секретом всех экземпляров. Секрет сохранять между перезапусками. Исходный пароль и секрет не записывать в Redis или журналы
1. Учитывать логин и пароль точно в полученном виде, без удаления пробелов и изменения регистра. IPv4 использовать в каноническом текстовом виде после проверки и разбора
1. Хранить whitelist и blacklist в общей PostgreSQL. Все экземпляры приложения используют основную БД; локальный кеш списков в первую реализацию не включать
1. Определять принадлежность IP обоим спискам двумя EXISTS в одном SELECT при Read Committed. При ошибке чтения завершать проверку до обращения к Redis.
1. Возвращать успех добавления или удаления подсети после фиксации изменения в БД. Новая проверка, начавшая чтение после подтверждения, учитывает изменение при отсутствии последующих изменений. Уже выполняющаяся проверка может завершиться по прежнему снимку
1. Принимать канонический IPv4 CIDR с явно указанной маской. Адрес с ненулевой хостовой частью отклонять с пояснением ожидаемой сети; одиночный адрес передавать с /32
1. Добавлять подсеть через ON CONFLICT (list_kind, subnet) DO NOTHING. Удалять точную запись из указанного списка. Отсутствие записи считать успехом.
1. Разрешить пересекающиеся сети и одинаковую подсеть в обоих списках. Сохранять приоритет blacklist; не удалять и не переносить запись из другого списка автоматически
1. Использовать интерфейс NetworkLists с Lookup(ctx, ip) (ListMembership, error), Add(ctx, list, subnet) error и Remove(ctx, list, subnet) error. Lookup возвращает принадлежность обоим спискам, а прикладная логика применяет приоритет
1. Использовать одну таблицу network_lists с обязательными полями list_kind типа text и subnet типа cidr. Разрешить только blacklist/whitelist и IPv4. Первичный ключ (list_kind, subnet) исключает дубликаты внутри списка; отдельный id не требуется
1. Для поиска сетей, содержащих IP (`subnet >>= ip`), использовать индекс `GiST (subnet inet_ops)`.
1. При проверке попытки требовать присутствия строковых полей `login` и `password`. Явно переданную пустую строку учитывать по общим правилам. Сохранять пробелы. В поле `ip` принимать один IPv4-адрес без маски. Нарушение этих правил возвращает ошибку валидации до обращения к спискам и счётчикам
1. Ограничить тело запроса проверки попытки 32 КиБ по фактически прочитанным данным, в том числе при распаковке. После декодирования допускать до 256 байт UTF-8 для `login` и до 4 096 байт UTF-8 для `password` включительно. При превышении любого предела отклонить запрос целиком до вычисления HMAC и обращения к хранилищам
1. Для первой реализации использовать HTTP API с JSON. Запрос проверки попытки содержит строковые поля `login`, `password` и `ip`. При завершённой проверке вернуть JSON-объект с логическим полем `ok`. Значение `false` означает штатный отказ по списку или лимиту
1. Проверять попытку через `POST /v1/attempts/check`. При завершённой проверке вернуть `200 OK` с `{"ok":true}`, если проверка разрешила попытку, или с `{"ok":false}`, если проверка отклонила попытку
1. Для `POST /v1/attempts/check` при превышении предела тела в 32 КиБ вернуть `413 Content Too Large`. Если размер тела укладывается в предел, при некорректном JSON, структуре запроса или нарушении требований к полям вернуть `400 Bad Request`. В обоих случаях завершить обработку до обращения к PostgreSQL и Redis
1. Для `POST /v1/attempts/check` вернуть `503 Service Unavailable`, если временная недоступность PostgreSQL или Redis помешала завершить проверку. При непредвиденной внутренней ошибке сервиса вернуть `500 Internal Server Error`
1. Для ответов `400`, `413`, `500` и `503` операции проверки вернуть JSON-объект с единственным строковым полем `error`. Категория ошибки определяется HTTP-кодом. При ошибке поля указать его имя и нарушенное правило. Значение пароля в сообщение не включать
1. Для `POST /v1/attempts/reset` передать хотя бы одно поле — `login`, `ip` или оба. Пустая строка выбирает счётчик пустого логина. Проверить весь запрос до вызова Reset. При ошибке валидации вернуть `400 Bad Request`. После успешного сброса всех указанных счётчиков вернуть `204 No Content`. Отсутствующий ключ считать успешно сброшенным
1. Передать все выбранные ключи в один вызов Reset. В Redis standalone удалить их одной командой `DEL`. После подтверждения вернуть `204 No Content`, в том числе при отсутствии ключей в Redis. При недоступности Redis или потере ответа вернуть `503 Service Unavailable`. После потери ответа результат команды неизвестен
1. Управлять подсетями через `/v1/lists/{list}/{address}/{prefix}` без тела запроса. PUT добавляет запись, DELETE удаляет. После фиксации вернуть 204, в том числе при повторной операции.
1. Задать предел памяти Redis через `maxmemory` и установить `maxmemory-policy noeviction`. Если Redis отклонил создание или обновление счётчика из-за нехватки памяти, завершить проверку с `503 Service Unavailable`. Действующие счётчики не вытеснять для освобождения памяти
1. Хранить счётчики только в памяти Redis. Отключить периодические снимки RDB (`save ""`) и журнал AOF (`appendonly no`). После перезапуска Redis начинать с пустого набора счётчиков
1. Использовать YAML для файла конфигурации Go-сервиса
1. При запуске прочитать YAML, применить явно заданные переменные `ABF_*` к соответствующим полям и проверить итоговую конфигурацию. При отсутствии переменной сохранить значение из файла. Пустая строка в окружении переопределяет значение YAML. При пустом итоговом секрете HMAC остановить запуск и указать имя параметра без его значения
1. Хранить в Git шаблон `config.example.yaml` со всеми полями конфигурации приложения и пустыми значениями секретов. Для локального запуска скопировать шаблон в `config.yaml`. Хранить локальный файл вне Git. Задать секреты в локальном файле или через окружение
1. Для локального запуска через Docker Compose задать в конфигурации Redis `maxmemory 64mb` (64 МиБ). При настройке лимита памяти контейнера предусмотреть запас сверх этого значения
1. Для сборки сервиса использовать `golang:1.27.4-trixie`. Для локального запуска через Docker Compose использовать `redis:8.10.3-trixie` и `postgres:18.7-trixie`
1. После проверки входных данных в HTTP-обработчике передать контекст запроса и одну попытку в `CheckAttempt`. Сервис определяет результат через `NetworkLists` и `BucketLimiter`. HTTP-обработчик формирует ответ по результату или причине ошибки
1. После проверки запроса на сброс передать выбранные логин и IP в `ResetBuckets`. Для пропущенного поля передать `nil`. Сервис передаёт все выбранные ключи в один вызов `BucketLimiter.Reset`
1. Разместить интерфейсы ограничителя и списков в `internal/antibruteforce`, реализации — в `internal/bucketlimiter/redis` и `internal/networklists/postgres`. Передавать реализации сервису из `cmd/antibruteforce`

## Контракты Go

```go
type Attempt struct {
    Login    string
    Password string
    IP       netip.Addr
}

func (s *Service) CheckAttempt(ctx context.Context, attempt Attempt) (bool, error)

type ResetTargets struct {
    Login *string
    IP    *netip.Addr
}

func (s *Service) ResetBuckets(ctx context.Context, targets ResetTargets) error
```

```go
type BucketLimiter interface {
    TryConsume(ctx context.Context, key BucketKey) (bool, error)
    Reset(ctx context.Context, keys []BucketKey) error
}
```

`BucketKey.Kind` задаёт признак ограничения, `Value` содержит его исходное значение. При ошибке игнорировать логический результат. Отмена контекста не откатывает списание.

```go
type NetworkLists interface {
    Lookup(ctx context.Context, ip netip.Addr) (ListMembership, error)
    Add(ctx context.Context, list ListKind, subnet netip.Prefix) error
    Remove(ctx context.Context, list ListKind, subnet netip.Prefix) error
}

type ListMembership struct {
    InBlacklist bool
    InWhitelist bool
}
```

При ошибке `Lookup` игнорировать результат `ListMembership`.
